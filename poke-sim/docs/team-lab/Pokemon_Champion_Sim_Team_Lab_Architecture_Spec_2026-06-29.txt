1. Executive Summary
This document defines a practical architecture for a Pokemon Champion competitive battle simulator with a Team Lab leaderboard. The system should not be treated as a simple damage calculator or a popularity ranking. It should be treated as a versioned evidence pipeline.
The core product idea is that every important output should be explainable: a legality result points to a ruleset and source status; a battle result points to a deterministic seed and replay event log; a leaderboard rank points to sim runs, engine version, ruleset version, regulation, sample size, and confidence.
Architecture sentence for Codex
Teams are validated against regulation-specific rulesets. Validated teams enter official or experimental sim pools. The battle engine runs deterministic battles and emits replay logs. Sim runs are stored with engine_version, ruleset_version, regulation_id, format, and seed. Analytics aggregates those runs into ratings, win rates, confidence labels, stale warnings, and matchup matrices. The UI displays rankings as simulator-derived evidence, never as unsupported official truth.

2. Non-Negotiable Product Principles
Evidence-bound accuracy: No rule, legality claim, or ranking should appear as certain unless it is tied to official data, in-game verification, replay verification, or an explicit source status.
Version everything: Every sim run, leaderboard entry, and legality report must include regulation_id, ruleset_version, engine_version, and format.
Unknown is not legal: When Champion-specific data is missing, return needs_verification instead of silently passing the team or mechanic as verified.
Separate mechanics, legality, and meta: A rule is not a trend, and a popular meta team is not automatically legal. These must remain separate data layers.
Deterministic simulation: Same teams, same ruleset package, same engine version, same seed, and same inputs should produce the same battle and replay log.
Stale results must be visible: When the engine or ruleset changes, affected leaderboard entries must be marked stale until recalculated.
Privacy by design: Custom teams can be private, public, or hidden-details. Hidden moves, items, EVs, IVs, natures, and tech choices must not leak to non-owners.

6. Team Validator
The Team Validator is the gate between Team Library and official simulation pools. It validates a team against a regulation-specific ruleset package and returns a structured report. It should never return only true or false.
Validate team size, bring size, level rules, format rules, duplicate species clause, and duplicate item clause.
Validate species, forms, moves, abilities, items, special mechanic eligibility, and any HOME or visitor constraints if relevant.
Return illegal when known rules are violated.
Return needs_verification when Champion source data is missing.
Return stale when the team was validated against an old ruleset and needs revalidation.
type LegalityReport = {   status: "verified" | "needs_verification" | "illegal" | "stale";   regulation_id: string;   ruleset_version: string;   errors: LegalityIssue[];   warnings: LegalityIssue[];   source_gaps: LegalityIssue[]; };  type LegalityIssue = {   code: string;   severity: "error" | "warning" | "needs_source";   message: string;   affected_slot?: number;   pointer?: string; };
Example validator behavior
If a team uses a form, item, or move that has not been source-verified for the selected Champion regulation, the validator should return needs_verification. That team may enter an experimental pool, but it must not enter official leaderboard scope.

7. Battle Engine
The Battle Engine is the protected core. It runs one battle from explicit inputs and returns a full event log. It should be deterministic and side-effect-free except for returning a result object. The battle engine should not know about leaderboards, user profiles, or popularity data.
Input
Description
Validated teams
Team A and Team B after legality validation.
Ruleset package
The exact regulation, format, clauses, and mechanic switches used for the battle.
Engine version
The battle engine version used to run this battle.
Seed
Random seed that makes the result reproducible.
Options
Max turns, timer mode, custom test flags, or scenario setup.

type BattleInput = {   team_a: ValidatedTeam;   team_b: ValidatedTeam;   regulation_id: string;   ruleset_version: string;   engine_version: string;   format: "singles" | "doubles";   seed: string;   options?: {     max_turns?: number;     timer_mode?: "ranked" | "tournament" | "custom";   }; };  type BattleResult = {   battle_id: string;   winner_team_id?: string;   result_reason: "ko" | "timer" | "draw" | "error";   turns: number;   engine_version: string;   ruleset_version: string;   regulation_id: string;   seed: string;   event_log: BattleEvent[];   confidence_flags: string[]; };

The replay system stores and displays the battle engine event log. QA uses replay logs to prove mechanics, debug engine regressions, and validate leaderboard results after engine or ruleset updates.

The Battle Engine runs one battle. The Sim Runner runs many battles: team-vs-team, team-vs-leaderboard, archetype sweeps, full leaderboard recalculation, targeted scenario sweeps, and QA regression jobs.

10. Analytics Aggregator
The Analytics Aggregator reads sim_runs and produces leaderboard entries, matchup matrices, archetype performance, confidence labels, and stale warnings. It should not run battles itself.
Filter sim runs by regulation_id, format, engine_version, and ruleset_version.
Exclude illegal teams from official leaderboard scopes.
Route needs_verification teams to experimental scopes only.
Aggregate wins, losses, draws, games played, raw win rate, adjusted win rate, and rating.
Assign confidence based on sample size, legality status, and confidence flags.
Mark results stale when engine or ruleset versions change.
rating formula v1:  raw_win_rate = wins / games_played  sample_confidence_multiplier: - games >= 10000: 1.00 - games >= 1000: 0.95 - games >= 100: 0.85 - otherwise: not ranked  legality_multiplier: - verified: 1.00 - needs_verification: 0.70 and experimental only - stale: 0.50 - illegal: excluded  rating = 1000 + ((adjusted_win_rate - 0.5) * 1000)  Keep this formula isolated so it can be replaced later with Elo, Glicko, or a team-specific rating model.

12. Matchups, Team DNA, and Compare My Team
12.1 Matchup Matrix
A pure leaderboard tells users what is ranked highly. The matchup matrix explains why. It should show team-vs-team and team-vs-archetype performance under the current regulation, engine version, and ruleset version.

12.2 Team DNA
Speed profile: fast offense, balanced, slow control, Trick Room-dependent.
Damage profile: physical, special, mixed, spread, single-target burst.
Defensive profile: fragile offense, bulky offense, balance, stall/control.
Dependency profile: weather, terrain, Mega, setup, redirection, speed control.
Variance profile: low, medium, high; high-roll dependency should be visible.
Skill profile: beginner-friendly, medium, high-skill, high-risk/high-reward.

19. Acceptance Criteria
Database migrations compile and apply cleanly.
Types exist for Team, TeamMember, SimRun, LeaderboardEntry, TeamMatchup, RulesetPackage, RuleFact, LegalityReport, and ReplayRecord.
Team visibility rules are represented in service logic and tested.
Illegal teams are excluded from official leaderboard scopes.
needs_verification teams are allowed only in experimental scopes unless later verified.
Leaderboard entries include regulation_id, format, engine_version, ruleset_version, sample size, confidence, and stale status.
Stale leaderboard entries are visibly marked in API and UI.
Hidden-detail teams do not leak hidden moves, items, EVs, IVs, natures, or tech choices to non-owners.
Unit tests cover raw win rate calculation, adjusted rating, confidence assignment, illegal exclusion, needs_verification handling, stale marking, and visibility filtering.
No Pokemon Champion-specific legality facts are hardcoded unless they come from a source-truth file in the repo.

Appendix A: Source and Research Notes
The implementation should maintain a source archive for official Champion regulation pages, official announcements, in-game rule screens, replay tests, and any baseline references such as Showdown. The app should distinguish source tiers and never collapse community meta into official game truth.
Source tier
Use for
Trust rule
Tier 1: official Champion/official Pokemon materials
Regulations, legal formats, official mechanics, dates.
Can verify rules when exact and current.
Tier 1: in-game screens and controlled replay tests
Mechanic verification and edge cases not documented publicly.
Can verify mechanics when captured and reproducible.
Tier 2: Pokemon HOME official material
Transfer/visitor constraints if relevant.
Use only for transfer and HOME-specific behavior.
Tier 2: Pokemon Showdown source/data
Baseline mechanic comparison and test oracle.
Reference only; not Champion truth unless verified.
Tier 3: tournament VODs and public teams
Meta observations and empirical matchup ideas.
Meta/coaching only, not legality.
Tier 4: Reddit/Discord/social claims
Leads for testing.
Never final truth without verification.

Final build rule
When in doubt, store the uncertainty. Do not hide it. Unknown mechanics, legal data, or source conflicts should be visible as source_gaps, needs_verification, confidence_flags, or stale warnings.
